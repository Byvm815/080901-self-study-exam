## 二、考点 1：软件需求分析

### （一）识记

**1. 需求分析的任务**
① 确定系统**必须做什么**（功能、性能、数据、界面、接口与约束）；
② 导出系统的**逻辑模型**（用 DFD、数据字典、判定表/树等表达），即"目标系统的模型"；
③ 编写**需求规格说明书**，作为**开发、测试与验收**的共同依据。

**2. 需求分析应遵循的原则（5 条）**
1. 必须**理解并表达问题的信息域**（数据与数据流）；
2. 必须**建立描述系统功能与行为的模型**（功能模型、数据模型、行为模型）；
3. 必须**对问题自顶向下、逐层分解**，并**区分"本质"与"实现"**（推迟实现细节）；
4. 必须使用**图表等可视化工具**表达需求（DFD、数据字典、判定表、判定树、结构化语言）；
5. 必须有**用户参与**，需求必须**一致、完整、无二义、可验证、可追溯、可修改**。

**3. 需求分析的 5 个步骤** ⚠️（按教材表述）
① **需求获取（调查研究）**：了解用户要求与现有系统的业务流程、数据与问题；
② **分析与综合**：去伪存真、建立 DFD/数据字典等分析模型，导出目标系统的逻辑模型；
③ **编写需求规格说明书**：把分析结果文档化（含数据字典）；
④ **需求评审（验证）**：与用户共同检查需求的一致性、完整性、可行性，形成评审结论；
⑤ **需求管理**：需求的变更控制与追溯（也可理解为"需求确认与基线化"）。
> 若教材采用经典 **4 步**（调查研究、分析与综合、书写文档、需求评审），按教材原话作答即可。

**4. 数据流图（DFD）的符号（必考）**

| 符号 | 名称 | 说明 |
|---|---|---|
| 圆形/圆角矩形 | **加工（变换/处理）** | 对数据进行的操作，名称用"动词+宾语" |
| 带箭头直线 | **数据流** | 箭头表示流动方向，旁标数据流名 |
| 开口矩形（或双横线） | **数据存储（文件）** | 数据的静态存储，如"订单表" |
| 矩形（方框） | **外部实体（源/宿）** | 系统之外的人/组织/系统 |

**5. 数据字典使用的符号**

| 符号 | 含义 | 示例 |
|---|---|---|
| `=` | **定义为** | 学生记录 = 学号 + 姓名 + 班级 |
| `+` | **与（顺序连接）** | 姓名 + 性别 |
| `[ … \| … ]` | **或（选择其一）** | [ 男 \| 女 ] |
| `{ … }` | **重复（0 次或多次）** | { 课程名 + 成绩 } |
| `( … )` | **可选（可有可无）** | ( 备注 ) |
| `…` | 重复/省略说明 | — |
| `**…**` | 注释（部分教材用） | — |

**6. 结构化分析（SA）的定义**
一种**面向数据流、自顶向下、逐层分解**的需求分析方法；以**数据流图 + 数据字典**为核心工具，配合**判定表、判定树、结构化语言**描述加工逻辑，建立系统的**逻辑（功能）模型**。

### （二）领会

**1. 需求规格说明书的主要内容**
① 引言（目的、范围、术语定义、参考资料）；② 任务概述（目标、用户特点、约束与假设）；③ **数据描述**（数据流图、数据字典、数据对象/ER 描述）；④ **功能需求**（功能划分与说明）；⑤ **性能需求**（时间、容量、精度）；⑥ **接口需求**（用户、硬件、软件、通信接口）；⑦ 设计约束（标准、语言、环境、安全）；⑧ 质量属性与**验收标准**；⑨ 附录（图表、索引）。

**2. 数据流图、数据字典、分层数据流图**
- **DFD 的作用**：从**数据流动与加工**的角度刻画系统"做什么"，是**结构化分析的核心工具**，也是结构化设计的输入。
- **数据字典（DD）的作用**：**定义 DFD 中每个成分（数据流、数据项、数据存储、加工）的确切含义**，与 DFD 配合构成系统的需求模型（"DFD 是骨架，DD 是血肉"）。
- **分层 DFD**：顶层（**上下文图**：整个系统画成一个加工，标出所有外部实体及其输入输出流）→ **0 层**（系统的几个主要功能）→ **1 层、2 层**……逐层细化。
- **平衡原则（父子平衡）**：父图中某个加工的**输入输出数据流**，必须与分解它的子图的输入输出数据流**一致**；同时**数据守恒**（不能凭空产生或消失）。

### （三）简单应用

**1. DFD 的作用及画法（步骤）**
① 确定系统**边界与外部实体**；② 找出系统的**输入输出数据流**，画顶层（上下文）图；③ 自顶向下**逐层分解**主要功能，画 0 层、1 层图；④ 为每个数据流、数据存储**命名并编号**；⑤ 检查**平衡与一致性**，避免"黑洞/奇迹"加工（只有输入没有输出，或反之）。
要点：**由外向内、自顶向下、逐层分解、数据流命名用名词、加工命名用"动词+宾语"**。

**2. 数据字典对不同类型的数据的描述方法**
- **数据流**：`数据流名 = 组成该数据流的数据项/数据结构`（如：订书单 = 书名 + 数量 + 单价 + 总金额）；
- **数据项（数据元素）**：说明**名称、别名、类型、长度/取值范围、默认值、说明**；
- **数据存储（文件）**：`文件名 = 记录构成 + 组织方式 + 存取方式 + 关键字`；
- **加工（基本加工/小说明）**：用**结构化语言、判定表、判定树**描述其加工逻辑（输入、处理、输出）。

**3. 结构化语言、判定表、判定树**
- **结构化语言（类 PDL）**：用自然语言 + 三种控制结构描述加工逻辑，只有**顺序、选择（if-then-else）、循环（while/until）**。
  ```
  若 金额 ≥ 1000 则
        若 是老客户 则 折扣 = 10%
        否则 折扣 = 8%
  否则
        若 金额 ≥ 500 则 …
  ```
- **判定表**：由**条件桩 + 条件项、动作桩 + 动作项**组成，把**所有条件组合**与相应动作列成表格，适合**条件组合复杂、逻辑严格**的加工。
- **判定树**：判定表的图形化表示，层次直观、易读，适合**条件判断有层次关系**的加工；缺点是规模大时易遗漏。

**4. 数据字典条目示例（图书借阅系统）**
```
借书单   = 借书证号 + 图书号 + 借出日期 + 归还期限
借书证   = 借书证号 + 读者姓名 + 单位 + 已借册数
读者记录 = { 借书证 + { 借书单 } }
借书证号 = 8{ 数字 }8            （附：类型=字符，长度=8，范围=00000001..99999999）
加工"借书" = 输入: 借书单; 处理: [ 校验借书证 | 校验图书 ] + 登记借出; 输出: 借出确认 + 修改后的读者记录
```

**5. 判定树示例（折扣规则）**
```
折扣决策
├── 金额 ≥ 1000 元
│   ├── 长期客户 → 10%
│   └── 非长期客户 → 8%
└── 金额 < 1000 元
    ├── 金额 ≥ 500 元
    │   ├── 长期客户 → 5%
    │   └── 非长期客户 → 3%
    └── 金额 < 500 元 → 无折扣
```

### （四）综合应用（大题套路）

**"进行结构化分析 + 画 DFD + 对分层 DFD 中的数据与加工进行说明" 答题步骤**
1. **确定系统范围与外部实体**（谁给系统什么、系统给谁什么）；
2. 画**顶层图（上下文图）**：一个加工 + 全部外部实体 + 输入输出流；
3. **分解功能**：画 0 层 DFD（3–6 个主要加工为宜），再按需分解到 1、2 层；
4. 标注**数据存储**与**编号**（如 1、1.1、1.1.1）；
5. **编写数据字典条目**：对每个数据流、数据存储、基本加工写出定义式/说明；
6. 检查**父图子图平衡、数据守恒、命名规范**。
> 得分点：外部实体齐全、加工命名规范、分层平衡、DD 条目完整（数据流组成 + 数据项类型长度 + 加工小说明）。

## 三、考点 2：软件设计

### （一）识记

**1. 软件设计的基本步骤**：**概要设计（总体设计）→ 详细设计**。

**2. 软件设计的任务（4 项）**：**数据设计、体系结构设计、接口设计、过程（构件级）设计**。

**3. 概要设计阶段的工作内容**
① 制定**设计规范/设计准则**；② 软件**体系结构（总体结构）设计**；③ **接口设计**（模块间接口、外部接口、人机接口）；④ **处理方式设计**；⑤ **数据结构（数据）设计**；⑥ 可靠性/安全性设计；⑦ 编写**概要设计文档**；⑧ **设计评审**。

**4. 设计规范的制定**：明确统一的设计**准则、命名规则、文档格式与评审标准**，保证设计的一致性、可读性与可维护性。

### （二）领会

**1. 软件体系结构总体设计需要完成的工作内容**
确定系统的**模块组成**、模块的**层次与调用关系**、模块的**接口与数据传递关系**，并用**结构图（SC 图）** 表示；同时确定**全局数据结构与关键算法策略**。

**2. 处理方式的设计涉及的内容**：**人机交互（界面）设计**、**输入输出格式与校验**、**错误与异常处理**、**并发/事务处理方式**、**运行环境与资源使用**、**安全与权限**等。

**3. 详细设计过程中需要完成的 3 个主要任务**
① 为每个模块确定**算法**（过程设计）；
② 设计模块内部的**数据结构**与接口细节；
③ 用图形/表格/语言工具**表达设计结果**，并进行**复杂度度量与评审**。

**4. 软件设计的基本策略**
① **自顶向下、逐步求精**；② **模块化**；③ **抽象**；④ **信息隐藏**；⑤ **模块独立性（高内聚、低耦合）**；⑥ 结构一致性与可复用。

**5. 数据结构设计包括的内容**：数据的**逻辑结构**、**存储（物理）结构**、数据元素的**组成与取值范围**、数据之间的**关系与操作**、**完整性/一致性约束**。

**6. 可靠性的含义**：软件在**规定的条件和规定的时间内**无故障运行的**能力（概率）**；包括**容错能力与健壮性**，常用 **MTBF（平均无故障时间）、MTTR（平均修复时间）、可用性**等度量。

**7. 模块的概念、基本属性、模块化的好处、模块的独立性**
- **模块**：由**数据说明、可执行语句等程序对象**组成的、可**单独命名**并可通过名字访问的程序单元（过程、函数、子程序等）。
- **基本属性**：**功能**（做什么）、**逻辑**（内部如何做）、**状态**（使用的数据与环境）。其中**功能与接口**构成模块的**外部特性**，**逻辑与状态**是**内部特性**。
- **模块化的好处**：分而治之**降低复杂度**；便于**分工与并行开发**；便于**测试、调试与修改**；提高**可理解性、可复用性与可靠性**；降低维护成本。
- **模块的独立性**：模块**功能单一明确、模块之间联系尽量少**，即"**高内聚、低耦合**"；是衡量设计质量最重要的标准。

**8. 分解、信息隐藏、模块独立性**
- **分解**：把大问题**自顶向下逐层划分为小问题**（模块），降低复杂度；
- **信息隐藏**：模块内部的**数据与实现细节对外不可见**，只通过接口访问，使修改局部化；
- **模块独立性**：由**分解 + 信息隐藏**保证，最终表现为**高内聚、低耦合**。

**9. 模块间的耦合（由弱到强，必背 7 级）**

| 级别 | 名称 | 含义 | 例 |
|---|---|---|---|
| 1（弱） | **非直接耦合** | 两模块无直接联系，仅通过上级模块通信 | 两个互不相干的模块 |
| 2 | **数据耦合** | 只传递**简单数据参数** | 传一个整数/字符串参数 |
| 3 | **标记耦合** | 传递**数据结构（记录）**，甚至只用了其中一部分 | 传整个学生记录但只用姓名 |
| 4 | **控制耦合** | 传递**控制信息（开关量）**，控制对方执行哪部分逻辑 | 传 flag 决定模块走哪个分支 |
| 5 | **外部耦合** | 都访问同一**外部数据格式/通信协议/设备** | 都读写同一外部文件格式 |
| 6 | **公共耦合** | 都访问同一**全局数据区（公共环境）** | 都用同一个全局变量表 |
| 7（强） | **内容耦合** | 一个模块**直接访问/修改另一模块内部数据**，或直接转入其内部 | 直接跳入别的模块内部标号 |

> 设计原则：**尽量使用数据耦合，少用控制耦合，限制公共耦合的适用范围，坚决避免内容耦合**。

**10. 模块内的内聚（由弱到强，必背 7 级）**

| 级别 | 名称 | 含义 | 例 |
|---|---|---|---|
| 1（弱） | **巧合（偶然）内聚** | 模块内各部分**毫无关系**，只是凑在一起 | 把不相干的语句放进同一模块 |
| 2 | **逻辑内聚** | 各部分**逻辑相似**，由传入参数决定执行哪一个 | "输出模块"按参数决定打印/显示/写文件 |
| 3 | **时间内聚** | 各部分在**同一时间段内执行** | 初始化模块 |
| 4 | **过程内聚** | 各部分**按特定次序执行**，无数据关系 | 先读入再判断流程 |
| 5 | **通信内聚** | 各部分**使用同一输入数据或产生同一输出数据** | 都基于同一订单计算统计量 |
| 6 | **信息（顺序）内聚** | 各部分对**同一数据结构**操作，且**前者的输出是后者的输入** | 先算总分再算平均分 |
| 7（强） | **功能内聚** | 各部分**共同完成单一、明确的功能**，缺一不可 | "计算平均分"模块 |

> 设计目标：**力争功能内聚，允许信息/通信内聚，避免巧合与逻辑内聚**。

**11. 概要设计阶段文档的构成**
**概要设计说明书**（软件结构、模块清单与功能说明、接口说明）、**数据结构/数据库设计说明**、**组装（集成）测试计划**、**用户手册初稿**、**模块开发卷宗**等。

## 四、考点 3：结构化系统设计

### （一）识记

**1. 软件结构的典型形式**：**变换型结构**、**事务型结构**（实际系统常为两者的复合）。

**2. 变换型系统的组成**：**输入（传入）部分 + 变换中心（处理）部分 + 输出（传出）部分**（加上输入/输出协调逻辑）。

**3. 事务型系统的特征与组成**
- **特征**：以**事务**（一组数据或一次请求）为中心，系统先**接收并分析事务类型**，再**分派**给相应的处理模块；
- **组成**：**事务中心（接收与分析、分派）+ 若干事务处理（活动）模块**。

**4. SC 图（结构图）的表示符号**

| 符号 | 含义 |
|---|---|
| 矩形 | **模块**（框内写模块名） |
| 带箭头（无圆点）的直线 | **调用关系**（由调用者指向被调用者） |
| 带**空心小圆**的短箭头 | **数据信息**的传递 |
| 带**实心小圆**的短箭头 | **控制信息**的传递 |
| 菱形 | **选择调用**（有条件地调用） |
| 弧形（半圆）箭头 | **循环调用** |

### （二）领会

**1. 变换型结构的基本模型**：顶层为**主控模块**，下设**输入协调模块**（处理所有逻辑输入）、**变换协调模块**（完成主要加工）、**输出协调模块**（产生所有逻辑输出）；三者再各自向下分解。

**2. 事务型结构的基本模型**：顶层**主控模块** → **事务中心模块**（分析事务类型）→ 各**事务处理模块**（按类型分支）；若某分支仍含输入—变换—输出，则再对该分支用**变换分析**细化。

### （三）综合应用

**1. 用变换分析法画 SC 图的步骤**
① **复审并细化 DFD**，确定加工与数据流；
② 找出**逻辑输入（传入）**、**逻辑输出（传出）**，夹在两者中间的是**变换中心**，从而**划定三条边界**；
③ 设计**顶层主控模块**（分配控制、协调）；
④ 为输入、变换、输出各设计**协调模块**及其下属模块（一个加工对应一个模块，自顶向下逐层映射）；
⑤ **优化**结构（合并小模块、提高独立性、单入口单出口）。

> **SC 图文本示意（变换分析结果）**
> ```
>             主控模块
>         ┌──────┼──────┐
>     输入协调  变换协调  输出协调
>        │         │         │
>     读入数据   计算处理   输出结果
> ```

**2. 用事务分析法画 SC 图的步骤**
① 识别**事务中心**与**事务类型**（由数据流的"类型标识"决定）；
② 设计**顶层主控模块** + **事务中心模块**（接收事务、判定类型、分派）；
③ 为每一类事务设计**事务处理模块**及其下级模块；
④ 若某事务分支中含变换流，则对分支再用**变换分析**细化；
⑤ 优化结构并检查接口。

**3. 对软件模块结构的改进（启发式规则，必背）**
1. **提高模块独立性**（高内聚、低耦合）；
2. 模块**规模适中**（一般 50–100 行/不超过一页纸）；
3. **深度、宽度适当**，**扇入大、扇出小**（扇出以 3–4 为宜，避免"病态"结构）；
4. 模块的**作用域应在其控制域内**（被影响的模块应在控制范围内）；
5. **降低接口复杂度**（少传参数、避免标记/控制耦合）；
6. 设计**单入口、单出口**模块；
7. 模块**功能可预测**（相同输入→相同输出，无副作用）。

## 五、考点 4：详细设计

### （一）识记

**1. 详细设计的目的与任务**
- **目的**：确定**每个模块的内部实现**，为编码提供**清晰、准确、无二义**的描述；
- **任务**：确定每个模块的**算法与处理逻辑、局部数据结构、接口细节**，并用工具表达出来（**不写具体源程序代码**）。

**2. 程序流程图的常用标准符号**：**起止框**（圆角矩形/椭圆）、**输入输出框**（平行四边形）、**处理框**（矩形）、**判定框**（菱形）、**准备框/初始化框**（六边形）、**流程线**（箭头）、**连接点**（小圆圈）、**注释框**。

### （二）领会

**1. 详细设计的原则**：① 采用**结构化构造**（顺序、选择、循环）；② **限制或避免使用 goto 语句**；③ **单入口单出口**；④ **自顶向下、逐步求精**；⑤ 结构清晰、易读易维护；⑥ 避免过深的嵌套与过长的模块；⑦ 设计结果**可验证、可评审**。

**2. 结构复杂性度量**
- **环域复杂度（McCabe 环路复杂度）**：衡量程序**逻辑复杂程度**与**所需基本路径数**：
  - **V(G) = 判定（判定点）数 + 1**
  - **V(G) = 边数 E − 节点数 N + 2**
  - 例：一个模块中有 3 个判定框 → V(G) = 3 + 1 = **4**，即至少需要 4 条测试路径才能覆盖所有独立路径。
  - 例（数图法）：设某流程图有 **7 个节点、9 条边** → V(G) = 9 − 7 + 2 = **4**，与"判定数 + 1"结果一致（该图有 3 个判定）。
  - **用途**：衡量模块逻辑复杂度、**确定基本路径测试所需用例数的下限**、判断模块是否过大（一般 V(G) ≤ 10 为宜）。
- **交叉点复杂度** ⚠️：以流程图中**交叉点的个数**衡量流程图的复杂程度——线条交叉越多，越难理解与维护；设计时应尽量减少交叉。

### （三）综合应用（必考表达工具）

**1. 程序流程图**：直观、易于表达，但**容易破坏结构化**（随意跳转），适合初学者与简单逻辑。

**2. N-S 图（盒图）**：**取消流程线**，用**嵌套的矩形**表示顺序、选择与循环，**强制结构化**，**单入口单出口**，缺点是修改与嵌套过深时不便。

```
┌────────────────────┐
│  读入 x, y          │  ← 顺序
├────────────────────┤
│  x > y ?           │
│ ┌──────┬─────────┐ │  ← 选择（条件成立在左，不成立在右）
│ │max=x │ max=y   │ │
│ └──────┴─────────┘ │
├────────────────────┤
│ while i ≤ n  ┌────┐│  ← 循环
│              │累加││
│              └────┘│
└────────────────────┘
```

**3. 伪代码（PDL）**：用自然语言 + 结构化控制结构描述算法，**易读、易修改、便于转成程序**，是详细设计中最常用的表达方式之一。
```
BEGIN
  读入 n
  若 n ≤ 0 则 输出"输入有误"
  否则
    sum ← 0; i ← 1
    WHILE i ≤ n DO
        sum ← sum + i
        i ← i + 1
    ENDWHILE
    输出 sum
END
```

**4. PAD 图（问题分析图）**：用**自左向右的阶梯式二维树形结构**表示程序逻辑，层次清晰、便于转成代码。

## 六、本章对比与易混点

| 易混点 | 正确理解 |
|---|---|
| DFD vs SC 图 | **DFD 面向数据流、与实现无关**；**SC 图面向模块与调用关系、是设计结果** |
| 耦合 vs 内聚 | **耦合看模块之间**（越小越好）；**内聚看模块内部**（越大越好） |
| 概要设计 vs 详细设计 | 概要=定**软件结构、接口、数据**；详细=定**每个模块的算法与内部逻辑** |
| 变换型 vs 事务型 | 变换型=**输入→变换→输出**；事务型=**事务中心分派**多个处理分支 |
| 环路复杂度 | V(G) = **判定数 + 1** = **边 − 点 + 2**，不是"节点数 + 1" |
