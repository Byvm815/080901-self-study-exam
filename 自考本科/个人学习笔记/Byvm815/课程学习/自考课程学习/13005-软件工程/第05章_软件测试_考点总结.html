第五章 软件测试 · 考点总结

本章重点：软件测试的目标、对象、步骤；黑盒法、白盒法、穷举测试法、选择测试法、边界值分析法；软件组装测试的方法；软件的调试方法；静态测试和动态测试
本章难点：根据具体问题选择合适的测试方法，设计黑盒法、白盒法、边界值分析、选择测试的测试用例
考查层次：本章是全书的第一大计算/设计题区（覆盖用例设计、边界值用例设计），名词与分类题也很多。

一、本章知识地图

  • 1. 软件测试概述：考纲要点：定义、步骤、对象；目标、原则；层次：识记+领会
  • 2. 软件测试的方法与技术：考纲要点：黑盒原理、等价类、白盒原理、穷举测试、选择测试、边界值测试目的；黑盒用例设计步骤、边界值选取原则；等价类划分与用例设计、6 种覆盖用例设计、边界值用例设计；层次：识记+领会+简单应用
  • 3. 单元测试：考纲要点：定义、步骤、5 个方面内容、驱动模块、桩模块；模块接口/局部数据结构/路径/错误处理/边界测试；层次：识记+领会
  • 4. 组装测试：考纲要点：4 种组装方式；自顶向下/自底向上的步骤与评价、计划考虑的问题、完成标志；层次：识记+领会
  • 5. 确认测试：考纲要点：任务、软件配置复审目的；阶段工作与步骤、有效性测试任务、系统测试任务、测试种类及适用阶段；层次：识记+领会
  • 6. 静态测试：考纲要点：静态分析的几种方法、静态错误分析工作内容；引用表、四类分析、人工测试 3 种；层次：识记+领会
  • 7. 调试技术：考纲要点：调试任务、调试活动的组成、调试方法；调试步骤、强行排错、回溯法、归纳法、演绎法、确定错误原则、修改错误原则；层次：识记+领会

二、考点 1：软件测试概述

（一）识记

  • 1. 软件测试的定义
    为了发现错误而执行程序的过程（广义：对需求分析、设计、编码各阶段成果（程序、数据、文档）进行的验证与确认活动）。

    Myers 的三个观点（常考）：① 测试的目的是发现错误；② 一个好的测试用例是能发现尚未发现的错误的用例；③ 一次成功的测试是发现了尚未发现的错误的测试。

  • 2. 软件测试的步骤（必背顺序）

  • 单元测试 → 组装（集成）测试 → 确认测试 → 系统测试（之后为验收测试/回归测试）。

  • 3. 软件测试的对象：程序、数据、文档（各阶段成果）。

（二）领会

  • 1. 软件测试的目标
    ① 验证软件是否满足需求规格说明；
    ② 尽早、尽可能多地发现并排除缺陷；
    ③ 通过测试建立对软件质量的信心（测试能证明有错，不能证明无错——Dijkstra：测试只能证明错误存在，不能证明错误不存在）。

  • 2. 软件测试工作应遵循的原则（必背）

  • 测试应尽早开始并贯穿软件开发全过程（测试用例可在需求、设计阶段就开始设计）；
  • 测试用例必须包含输入数据与预期输出；
  • 程序员应避免测试自己编写的程序，测试宜由独立第三方进行；
  • 设计用例时既要包含合理、有效的输入，也要包含不合理、无效的输入；
  • 严格执行测试计划，避免随意、盲目测试；
  • 妥善保存测试计划、用例、结果与缺陷记录，便于回归测试；
  • Pareto 原则：80% 的错误可能集中在 20% 的模块中，对错误聚集的模块应重点测试；
  • 穷举测试不可能，应选择有限但有代表性的测试用例。

三、考点 2：软件测试的方法与技术

（一）识记

  • 1. 黑盒测试原理：不考虑程序内部结构与处理过程，只依据功能需求/规格说明，通过输入与输出的对应关系检验功能是否正确；又称功能测试；主要用于确认测试、系统测试。

  • 2. 等价类：把输入域划分为若干子集合（等价类），同一等价类中的任意数据对发现错误的作用相同，取一个代表值即可代表整类；分为有效等价类与无效等价类。

  • 3. 白盒测试原理：依据程序内部逻辑结构设计用例，检验每条路径、每个逻辑判断是否按预期工作；又称结构测试；主要用于单元测试。

  • 4. 穷举测试的定义：把所有可能的输入数据组合（黑盒）或所有可能的执行路径（白盒）都测试一遍。实际上不可行（组合爆炸、路径爆炸）。

  • 5. 选择测试的定义：在时间、成本、人力等资源有限的条件下，有选择地设计少量但有效的测试用例，以尽可能多地发现错误（即以有限用例达到可接受的覆盖）。

  • 6. 边界值测试的目的：大量错误发生在输入/输出范围的边界上，故取边界值及其邻近值设计用例，以发现边界处理错误（如 < 与 ≤ 用错、数组越界、循环次数差一）。

（二）领会

  • 1. 设计黑盒法测试用例的步骤
    ① 分析需求规格说明，划分有效等价类与无效等价类并编号；
    ② 设计用例使其尽可能多地覆盖尚未覆盖的有效等价类（一个用例可覆盖多个有效等价类）；
    ③ 为每一个无效等价类各设计一个用例（避免相互屏蔽）；
    ④ 结合边界值分析补充用例；
    ⑤ 写出预期输出，形成测试用例表；
    ⑥ （可选）用因果图/判定表处理输入条件之间的组合关系。

  • 2. 边界值分析方法选择测试用例的原则
    ① 若输入是取值范围（如 1 ≤ x ≤ 100）：取 min、min+、nom、max−、max 以及略小于 min、略大于 max 的值（即"七点法"：min−, min, min+, nom, max−, max, max+）；
    ② 若输入是有序集合/表格：取第一个元素和最后一个元素；
    ③ 若输入受条件约束（如"最多 n 个字符"）：取 n 与 n+1；
    ④ 若程序内部有数据结构：取其边界（数组下标 0 与 n−1、n）；
    ⑤ 同时考虑输出域的边界；
    ⑥ 通常与等价类划分结合使用（等价类取"典型值"，边界值取"边缘值"）。

（三）简单应用（必考用例设计）

  • 1. 等价类划分与用例设计（示例：输入 x 要求 1 ≤ x ≤ 100 的整数）

  • 有效：编号：①；1 ≤ x ≤ 100 的整数；代表用例：x = 50

  • 无效：编号：②；x < 1（如 x = 0、−5）；代表用例：x = 0
  • 无效：编号：③；x > 100（如 x = 101）；代表用例：x = 101

  • 无效：编号：④；非整数/非数字（如 3.5、"abc"、空）；代表用例：x = "abc"

  • 2. 白盒测试六种覆盖的测试用例设计（经典例题）

PROCEDURE P1
  INPUT (A, B, X)
  IF (A > 1) AND (B = 0) THEN X = X / A ENDIF      ← 判定1：条件 c1(A>1)、c2(B=0)
  IF (A = 2) OR  (X > 1) THEN X = X + 1 ENDIF      ← 判定2：条件 c3(A=2)、c4(X>1)
  OUTPUT (X)

注意：X 在第一个判定中被修改，会影响第二个判定，设计用例时要先算最终值。

  • 语句覆盖：每个可执行语句至少执行一次；用例（A, B, X）：① (2, 0, 3)；两个判定均取真 → 所有语句执行；最弱
  • 判定（分支）覆盖：每个判定的真、假分支都执行一次；用例（A, B, X）：① (2, 0, 3)；② (1, 1, 1)；① 判定1真、判定2真；② 判定1假、判定2假
  • 条件覆盖：每个判定中每个条件取真、取假各一次；用例（A, B, X）：① (2, 0, 3)；② (1, 1, 1)；两组用例使 c1–c4 均取真、取假
  • 判定-条件覆盖：同时满足判定覆盖与条件覆盖；用例（A, B, X）：① (2, 0, 3)；② (1, 1, 1)；兼顾两者的不足，但不保证条件组合全覆盖
  • 条件组合覆盖：每个判定中条件取值的所有组合至少出现一次；用例（A, B, X）：① (2, 0, 3)；② (2, 1, 1)；③ (1, 0, 3)；④ (1, 1, 1)；判定1 的 c1c2 与判定2 的 c3c4 全覆盖

  • 路径覆盖：程序中所有可能的执行路径至少执行一次；用例（A, B, X）：① (2, 0, 3)：判1真/判2真；② (3, 0, 1)：判1真/判2假；③ (1, 0, 3)：判1假/判2真；④ (1, 1, 1)：判1假/判2假；最强（本例 4 条路径全覆盖；含循环时不可穷举）

  • 覆盖强度顺序：语句覆盖 ＜ 判定覆盖 ＜ 条件覆盖/判定-条件覆盖 ＜ 条件组合覆盖 ＜ 路径覆盖。

    关键结论：条件覆盖不一定包含判定覆盖；判定-条件覆盖不一定包含条件组合覆盖；路径覆盖最强但通常不可实现。

  • 3. 边界值分析用例设计（示例：1 ≤ x ≤ 100 的整数）
    取：x = 0（min−）、1（min）、2（min+）、50（nom）、99（max−）、100（max）、101（max+）；
    若输入是字符串长度上限 8，则取 8 与 9；若输入是数组下标，则取 0、n−1、n。

四、考点 3：单元测试

（一）识记

  • 1. 单元测试的定义：对软件中最小的可测试单元（模块/构件/函数） 进行的测试，验证其接口、内部数据结构、逻辑路径、错误处理与边界是否正确。

  • 2. 单元测试的步骤 【注意】：① 制定单元测试计划；② 依据详细设计设计测试用例；③ 编写驱动模块与桩模块（测试台/测试脚手架）；④ 执行测试并记录结果；⑤ 分析结果、修正错误并回归测试。

  • 3. 单元测试 5 个方面的内容（必背）

  • 模块接口测试；
  • 局部数据结构测试；
  • 重要的执行路径测试（路径测试）；
  • 错误处理路径测试；

  • 边界条件测试。

  • 4. 驱动模块（Driver）：模拟调用被测模块的上层模块，负责向被测模块传送测试数据、调用它并接收结果（相当于"主程序"）。

  • 5. 桩模块（Stub）：模拟被测模块所调用的下层模块，用简单代码返回预期的（或固定的）数据，以便被测模块能运行。

（二）领会

测试方面 主要检查内容
模块接口测试 参数个数、类型、顺序是否正确；形参与实参是否匹配；返回值是否正确；全局变量/外部数据的使用是否正确；文件读写的打开、关闭与格式
局部数据结构测试 变量是否初始化/未定义使用；类型是否一致（整型/实型混用）；变量名拼写与作用域；数组/字符串越界；指针与动态内存使用
路径测试 基本路径与独立路径是否按预期执行；判定条件是否正确（< 与 ≤、AND 与 OR）；循环的初值、次数、终止条件；是否存在不可达代码
错误处理测试 是否能预见并处理错误（除零、越界、文件不存在）；错误提示是否清晰；异常分支是否能正确返回；错误处理本身是否会引发新错误
边界测试 数据流的最大值/最小值、数组边界、循环的第 0 次与最后一次、正好等于边界与刚好越界的情形

五、考点 4：组装测试

（一）识记

  • 组装测试（集成测试）的 4 种组装方式（必背）
  • 自顶向下组装（Top-Down）；
  • 自底向上组装（Bottom-Up）；
  • 自顶向下与自底向上相结合（混合/三明治式）；
  • 一次性组装（大爆炸式/整体组装）。

（二）领会

  • 1. 自顶向下组装测试的步骤
    ① 以主控模块作为测试起点（作为驱动模块）；
    ② 沿控制层次自顶向下逐层加入模块，尚未加入的下层模块用桩模块代替；
    ③ 可采用深度优先（先打通一条主路径）或广度优先（逐层横向加入）策略；
    ④ 每加入一个（或一组）模块就做一次测试，通过后再加入下一层，直至全部组装完成。

  • 2. 自顶向下组装测试的评价

  • 优点：能较早验证主要控制与决策逻辑（高层结构）、较早发现接口与设计错误、可在早期向用户演示骨架版本、需要桩模块但可复用；

  • 缺点：需要编写大量桩模块；底层关键模块（算法、输入输出）的测试被推迟，问题发现晚；桩模块可能掩盖底层真实行为。

  • 3. 自底向上组装测试的步骤
    ① 从最底层模块（不再调用其他模块的模块）开始，把紧密相关的一组模块组成簇（cluster）；
    ② 为每个簇编写驱动模块调用它，先对簇做测试；
    ③ 逐层向上合并，用驱动模块调用下级已测好的簇，边合并边测试，直至顶层。

  • 4. 自底向上组装测试的评价

  • 优点：不需要桩模块；底层模块（关键算法与输入输出）得到充分测试，问题早发现；

  • 缺点：需要编写大量驱动模块；程序整体骨架直到后期才形成，高层控制与设计错误发现晚；不便早期向用户演示。

  • 5. 组装测试计划时应考虑的问题 【注意】
    ① 组装的顺序与策略（自顶向下/自底向上/混合/一次性）；② 驱动模块与桩模块的准备与工作量；③ 模块接口与数据传递的正确性（参数、全局数据、文件）；④ 回归测试的安排；⑤ 集成频度（持续集成）与版本管理；⑥ 测试环境、工具与人员、进度安排。

  • 6. 组装测试完成的标志
    ① 所有模块按计划全部组装完毕；② 接口测试全部通过，模块间数据传递正确；③ 主要功能已能协作运行；④ 回归测试无严重缺陷；⑤ 组装测试报告与缺陷记录完成并归档。

六、考点 5：确认测试

（一）识记

  • 1. 确认测试（Validation Testing）的任务：验证软件是否满足需求规格说明书的全部要求——即"证实我们做对了产品"（有效性验证），由有效性测试 + 软件配置复审两部分组成。

  • 2. 软件配置复审的目的：保证所有交付物（文档、程序、数据）齐全、一致、正确、可追溯，配置管理与变更记录完整，为交付与后续维护提供依据。

（二）领会

  • 1. 确认测试阶段需要完成的工作及步骤 【注意】：① 制定确认测试计划；② 进行有效性测试（黑盒法）；③ 进行软件配置复审；④ 进行验收测试（α 测试、β 测试）；⑤ 记录缺陷并修正、回归；⑥ 编写确认测试报告，通过后交付。

  • 2. 有效性测试的任务：在模拟用户环境下，用黑盒测试验证软件的功能、性能、界面、文档等与需求规格说明是否一致（是否满足所有需求与验收标准）。

  • 3. 系统测试的任务：把软件与硬件、网络、其他软件/数据集成在一起，在实际运行环境中测试整个计算机系统，验证其是否满足系统要求（功能、性能、强度、安全、兼容、恢复、可靠性、安装、文档等）。

  • 4. 软件测试的种类及其适用阶段

测试种类 目的/内容 适用阶段
单元测试（白盒为主） 验证模块内部逻辑、接口、数据结构 编码完成后
组装/集成测试 验证模块间接口与协作 模块组装时
确认测试（黑盒） 验证是否满足需求规格说明（有效性 + 配置复审） 组装完成、交付前
系统测试（黑盒） 验证整个系统在实际环境中的表现 交付前的整体系统
验收测试（α/β） 由用户验证是否可接受 交付前/交付时
功能测试 功能正确性 确认/系统测试
性能测试 响应时间、吞吐量、资源占用 系统测试
强度（压力）测试 极限负载下的表现 系统测试
安全测试 权限、数据安全、防攻击 系统测试
兼容性测试 不同软硬件/平台环境 系统测试
恢复测试 故障后的恢复能力 系统测试
可靠性测试 MTBF 等可靠性指标 系统测试

七、考点 6：静态测试

（一）识记

  • 1. 程序静态分析的几种方法（识记）
    ① 引用表（数据/引用表）分析；② 变量类型分析；③ 引用分析；④ 表达式分析；⑤ 接口分析。

    即：不运行程序，通过分析源程序的语法、结构与数据流发现错误。

  • 2. 静态错误分析的工作内容
    检查语法与语义错误、类型不匹配、变量未初始化或未使用、数组越界、参数与接口不一致、不可达代码、死循环、表达式中的除零与括号不匹配、违反编码规范等。

（二）领会

  • 1. 在程序的静态分析中使用各种引用表
    常用：变量引用表（定义—使用表）、标号引用表、过程/函数调用表、常量表、文件与数据引用表。
    用途：检查变量是否"先定义后使用"、是否有定义未使用/使用未定义、标号是否有效、调用与被调用是否一致，以及数据流异常（未初始化、死代码）。

  • 2. 错误分析的四类

  • 变量类型分析：检查变量类型与使用是否匹配（整型/实型混用、数组维数与下标类型、赋值类型兼容）；
  • 引用分析：检查变量/过程是否被定义而未引用、或引用而未定义；参数传递是否一致；
  • 表达式分析：检查括号匹配、除零、下标越界、类型不兼容、运算优先级引起的错误；

  • 接口分析：检查模块间参数个数、类型、顺序、返回值、全局量是否一致。

  • 3. 人工测试的三种方式（必背）

  • 桌前检查（代码自查）：由程序员本人按检查表审查自己的代码；特点：成本低，但受"自查盲区"限制

  • 代码评审（代码会审/审查）：由评审小组按规程逐行审查代码，对照错误清单（如常见缺陷检查表）；特点：系统、严格，发现问题多，但耗时、需组织
  • 走查（遍历/演示）：由测试者/评审者提出测试数据，在纸面或脑中"走"程序，作者讲解、评审者质疑；特点：以人为"执行器"，能发现逻辑与理解偏差

八、考点 7：调试技术

（一）识记

  • 1. 程序调试（Debug）的任务：在测试发现错误之后，确定错误的准确性质与位置并加以排除（修正）。

  • 2. 调试活动的组成 【注意】：确定错误的位置（定位）→ 分析错误原因 → 修改设计与代码 → 重新测试（回归验证）。

  • 3. 调试可采用的方法（必背）
    ① 强行排错法（蛮干法）；② 回溯法；③ 归纳法；④ 演绎法；⑤ 对分查找法（原因排除法/二分法）。

（二）领会

  • 1. 程序调试的步骤：① 从错误征兆入手；② 确定错误的性质与位置；③ 找出产生错误的原因；④ 提出并选择修改方案；⑤ 修改代码并回归测试（确认修正且未引入新错误）。

  • 2. 强行排错的方法：在程序中插入打印语句（输出中间变量）、设置断点、单步跟踪、转储内存/调用栈、使用调试器查看变量与表达式。特点：直观、易上手，但效率低、可能引入新问题，适合错误范围较小或有工具支持时。

  • 3. 回溯法排错的基本方法：从错误征兆出现的位置开始，沿程序逻辑（控制流）逐步向前回溯，检查各步的数据与逻辑，直到找到错误的源头。适合小型程序；程序大时回溯路径过多、效率低。

  • 4. 归纳法排错的步骤（必背顺序）
    ① 收集与错误有关的所有数据（测试结果、征兆、日志）；
    ② 整理数据，找出规律（哪些输入出错、哪些不出错）；
    ③ 提出假设（关于错误原因的推测）；
    ④ 用数据/实验证明假设是否成立；
    ⑤ 若假设不成立，回到②修正假设；成立则修正错误并回归测试。

  • 5. 演绎法排错的主要步骤（必背顺序）
    ① 列举所有可能的原因（提出多个假设）；
    ② 用已有数据排除、细化这些假设（缩小范围）；
    ③ 对剩下的假设进行证明（设计实验验证）；
    ④ 确定并修正错误，回归测试。

  • 6. 确定错误性质与位置的原则
    ① 先分析错误征兆，再动手修改（不要急于改代码）；
    ② 思考在前：先想清楚"错误可能在哪、为什么"，再用调试工具；
    ③ 不要轻易怀疑"不可能出错"的地方，也不要一次改多处；
    ④ 若长时间无进展，暂时放下问题，稍后再分析；必要时向他人求助（讲解问题常能带来灵感）；
    ⑤ 保存现场（记录数据、日志、运行环境），避免破坏证据。

  • 7. 修改错误的原则
    ① 修改前必须确认错误原因，避免"改症状不改病因"；
    ② 一次只修改一个错误（便于判断效果）；
    ③ 修改后立即回归测试，确认原功能未被破坏；
    ④ 修改要考虑连带影响（副作用）：代码、数据、文档；
    ⑤ 修改错误的概率与引入新错误的概率成正比，故修改要谨慎、局部化；
    ⑥ 记录修改内容、原因、时间与验证结果，更新文档。

九、考点 8：软件测试工具

（一）识记

  • 1. 静态分析工具的组成 【注意】：词法/语法分析器（语言分析器）＋ 数据（引用）表生成器 ＋ 错误分析与报告输出模块（＋ 与源程序库/配置库的接口）。

  • 2. 测试数据自动生成工具的分类
    ① 路径测试数据生成器（按路径/条件求解生成数据，白盒）；
    ② 随机测试数据生成器（按分布随机产生输入）；
    ③ 面向数据（输入域）的生成器（按等价类、边界值等规则生成，黑盒）。

  • 3. 动态测试工具按功能的分类 【注意】
    ① 测试覆盖监视程序；② 动态断言处理程序；③ 符号执行工具；④ 测试结果分析程序；⑤ 模块测试台（驱动/桩 + 数据管理）；⑥ 集成测试环境（以上工具的集成）。

（二）领会

  • 1. 静态分析工具的功能：在不运行程序的情况下分析源程序，报告语法/语义问题、可疑结构与数据流异常（未初始化变量、不可达代码、接口不一致）、复杂度与编码规范违反，输出引用表与告警清单。

  • 2. 测试覆盖监视程序的工作过程：对源程序进行插装（instrument，插入计数/标志语句） → 运行被测程序 → 记录语句/判定/条件/路径的执行情况 → 运行结束后与总计数比较，输出覆盖率报告。

  • 3. 动态断言处理程序的工作过程：在程序中插入断言（assert）语句 → 运行到断言处时求值 → 若为假则报告错误位置与上下文信息（变量值、调用栈）→ 便于快速定位错误。

  • 4. 符号执行结果的两个用途：① 作为路径测试数据的生成/选择依据（求解路径约束得到输入数据）；② 用于程序正确性验证/分析（发现不可达路径、路径约束矛盾、除零等潜在错误）。

  • 5. 测试结果分析程序的功能：把实际输出与预期输出比较，对结果分类、汇总、标记差异，生成测试报告，便于判断通过/失败与统计缺陷。

  • 6. 模块测试台的功能：为单元测试提供驱动模块、桩模块、测试数据准备与执行控制、结果记录的支撑环境，使单个模块能独立运行与验证。

  • 7. 集成测试环境的构成和作用

  • 构成：测试驱动/桩、测试数据生成器、覆盖监视、结果分析、缺陷记录与配置管理等工具的集成；
  • 作用：支撑模块组装后的集成测试，统一管理用例、执行与结果，提高效率、可重复性与可追溯性。

十、本章对比与易混点

易混点 正确理解
黑盒 vs 白盒 黑盒=功能测试，不看内部结构，用于确认/系统测试；白盒=结构测试，看内部逻辑，用于单元测试
穷举测试 vs 选择测试 穷举=测遍所有输入/路径（不可行）；选择=有限资源下选有代表性的用例
等价类 vs 边界值 等价类取代表值（典型值）；边界值取边界及其邻域值；两者常结合使用
语句覆盖 vs 判定覆盖 语句覆盖最弱（判定全真即可）；判定覆盖要求真假分支各执行一次
条件覆盖 vs 判定-条件覆盖 条件覆盖不保证判定覆盖；判定-条件覆盖同时满足判定与条件覆盖
驱动模块 vs 桩模块 驱动=模拟上层调用者（自底向上时需要）；桩=模拟下层被调用者（自顶向下时需要）
确认测试 vs 系统测试 确认=验证是否满足需求规格说明；系统=软硬件集成后验证整个系统
测试 vs 调试 测试=发现错误（系统性、有计划）；调试=定位并排除错误（在测试之后）
