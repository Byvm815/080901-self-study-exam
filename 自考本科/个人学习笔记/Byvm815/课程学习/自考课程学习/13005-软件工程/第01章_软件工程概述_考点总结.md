## 二、考点 1：软件（识记）

- **1. 软件的定义（必背原话要点）**
软件 = **程序 + 数据 + 文档**。
- **程序**：按事先设计的功能和性能要求执行的**指令序列**；
- **数据**：使程序能正常操纵信息的**数据结构**；
- **文档**：与程序开发、维护和使用有关的**图文材料**。

- **2. 软件的特点（高频简答/多选，7 条）**
- **软件是逻辑产品**，具有抽象性，没有物理实体，其正确性难以直接度量；
- 软件的生产主要是**脑力劳动**，成本集中在**开发（人力）**，而非原材料与制造；
- 软件**不存在磨损、老化**问题（不会用坏），但会因**反复修改而"退化"（变坏）**；
- 软件的开发与运行**依赖硬件和支撑环境**（计算机系统、OS、工具），受环境制约；
- 软件**复制成本极低**，但**开发与维护成本高**，维护费用在生命周期总成本中占大头；
- 软件具有**复杂性**，逻辑复杂、状态多，难以完全测试；
- 多数软件需要**定制开发**，**生产率提高缓慢**，且受人为因素影响大。

> 易错点：软件"没有磨损"≠"不会失效"；软件维护成本**高于**开发成本。

## 三、考点 2：软件工程（识记 + 领会）

- **1. 软件工程的定义（必背，两种表述都记）**
- **IEEE（1993）**：① 把**系统化、规范化、可度量**的途径应用于软件的**开发、运行和维护**，也就是把**工程化**应用于软件；② 对①中所述途径的**研究**。
- **通俗表述**：软件工程是**指导软件开发和维护的一门工程学科**，采用工程的概念、原理、技术和方法，以**在给定成本与进度下，开发出高质量、可维护的软件**为目标。

- **2. 软件工程的研究领域（识记，答"包含哪些内容"）**
- **软件开发方法**（结构化方法、面向对象方法、敏捷方法等）；
- **软件开发工具与环境**（CASE 工具、IDE、测试工具）；
- **软件过程**（过程模型、过程改进、软件生命周期）；
- **软件工程管理**（软件项目管理：计划、成本、进度、风险、人员）；
- **软件质量与测试**（质量保证、软件测试、评审）；
- **软件维护**与软件配置管理。

- **3. 软件危机面临的问题（领会，必背 7 条）**
- 对软件开发**成本和进度**的估计常常很不准确；
- 用户对"已完成的"软件系统**不满意**的现象经常发生；
- 软件产品的**质量往往靠不住**；
- 软件常常是**不可维护**的；
- 软件通常**没有适当、完整的文档资料**；
- 软件成本在计算机系统总成本中所占**比例逐年上升**；
- 软件开发**生产率的提高**远远跟不上计算机应用迅速普及深入的趋势。

> 软件危机的**根源**：软件规模与复杂度迅速增长；缺乏工程化的方法与工具；忽视需求分析与文档；管理薄弱、估算靠经验。  
> **解决途径**：软件工程（工程化方法 + 工具 + 过程管理 + 质量保证）。

## 四、考点 3：软件过程（识记）

- **1. 软件过程（Software Process）的定义**
为获得高质量软件所需完成的一系列**任务的框架**，即把**人员、技术、工具、方法**组织起来完成软件开发的**活动集合**。

- **2. 软件过程模型（过程范型）的定义**
对软件过程的**抽象描述/简化表示**，规定了软件开发活动的**阶段划分、顺序、任务与产出**，用以指导软件开发的组织与实施。

- **3. 软件过程包含的 4 种基本活动（必背）**
① **软件规格说明**（Specification）——确定软件的功能与约束；  
② **软件开发**（Development）——设计并实现软件；  
③ **软件确认**（Validation）——确认软件满足需求；  
④ **软件演进**（Evolution）——随需求与环境变化而修改演进。

- **4. 软件开发的一般性过程**（学习目的要求"掌握"）
问题定义 → 可行性研究 → 需求分析 → 设计（概要、详细）→ 编码 → 测试 → 运行维护。
> 三阶段概括：**软件定义 → 软件开发 → 运行维护**。

- **5. 各阶段的目标与任务（识记，易与第二章重考）**

- **需求分析**：目标：确定"**做什么**"，导出系统逻辑模型；主要任务：需求获取与调查、建立功能/数据模型（DFD、数据字典）、编写**需求规格说明书**、需求评审
- **软件设计**：目标：确定"**怎么做**"；主要任务：把需求转化为软件内部结构：**数据设计、体系结构设计、接口设计、过程（构件级）设计**
- **软件设计的步骤**：目标：—；主要任务：**概要设计（总体设计）→ 详细设计**
- **软件实现**：目标：把设计变成可运行产品；主要任务：**编码**（用程序设计语言实现）、**单元测试与调试**、代码评审、编写程序文档

## 五、考点 4：软件过程模型（领会 · 本章大题区）

### 1. 瀑布模型

- **阶段划分（逐级下落）**：问题定义/可行性研究 → **需求分析 → 概要设计 → 详细设计 → 编码 → 测试 → 运行维护**。
- **各阶段任务**：需求分析=明确"做什么"并形成文档；设计=定体系结构、接口、数据结构、算法；编码=实现程序；测试=发现并排除错误；维护=修改、完善。**前一阶段的文档是后一阶段的输入**，每阶段结束有**评审**。
- **优点**：阶段清晰、文档规范、便于分工与项目管理；适合**需求明确且稳定、技术成熟、规模中等**的项目。
- **存在的问题**：① **缺乏灵活性，难以适应需求变化**（需求变更代价极大）；② 用户要等到**项目末期**才能看到可运行产品，**缺乏早期反馈**；③ **风险后置**，错误发现晚、修复代价高；④ 阶段间以文档"冻结"衔接，**反馈与回溯困难**，容易产生"文档驱动"而不顾用户真实需求。

### 2. 原型模型（快速原型）

- **软件开发过程**：需求（快速）获取 → **快速设计并建立原型** → 用户**试用与评价** → **修改、细化原型** →（反复迭代直到需求确认）→ 按确认需求正式开发/交付。
- **两种用法**：**丢弃型原型**（仅用于确认需求，用完丢弃）、**演化型（增量式）原型**（逐步演化为最终产品）。
- **适用**：需求**不明确、不确定**、用户难以事先说清要求的系统。
- **存在的问题**：① 用户**容易把原型误认为成品**，提出过高要求、要求"直接上线"；② 为求快而采用**不合适的实现方法**，导致**质量与性能差**；③ 迭代可能**失控**，缺少整体规划与文档，管理难度大；④ 原型与最终产品可能不一致，误导用户。

### 3. 螺旋模型（Boehm）

- **特点（必背）**：把**瀑布模型与原型模型结合**，并**加入风险分析**；是一种**迭代的、风险驱动的**过程模型，沿螺旋线由内向外逐步展开，每转一圈得到一个更完善的版本。
- **按螺旋模型进行软件开发的过程（4 个象限/活动，每轮重复）**：
- **制定计划**：确定本轮目标、可选方案与约束条件；
- **风险分析**：评价方案、**识别与消除风险**（必要时建立原型验证）；
- **实施工程**：开发并验证本阶段产品；
- **客户评价**：客户评审本轮成果，提出修改意见，规划下一轮。
- **适用**：**大型、高风险**项目（尤其内部开发的大型软件）。
- **局限**：需要**风险分析专家**，模型较复杂，小项目使用不经济；风险分析不当会带来更大风险。

### 4. 统一过程模型（RUP）

- **三大特点**：**用例驱动、以体系结构为中心、迭代与增量**。
- **5 个工作阶段及工作内容（必背）**

| 阶段 | 主要工作内容 | 主要产出 |
|---|---|---|
| **① 初始（起步）阶段** | 确定**项目范围与业务用例**，进行可行性分析与风险识别，明确系统构想 | 构想文档、初始用例模型、初步风险评估 |
| **② 细化（精化）阶段** | 建立**体系结构基线**，分析问题域、确定并细化用例，制定项目计划，消除最高风险 | 用例模型（细化）、体系结构描述、项目计划 |
| **③ 构建阶段** | **迭代开发**所有剩余构件与功能，集成并测试，形成可交付版本 | 可运行的 β 版本、测试与用户文档 |
| **④ 移交（交付）阶段** | **β 测试、用户培训、数据转换、缺陷修正、产品发布** | 正式发布版本 |
| **⑤ 产品化（生产/维护）阶段** 【注意】 | 产品投入运行后的**运行支持与演进维护** | 维护版本、问题报告 |

> 【注意】 部分教材将 RUP 概括为"初始、细化、构建、移交"4 个阶段（产品化并入移交/维护），答题时按指定教材表述。  
> 补充：RUP 有 **6 个核心过程工作流**（业务建模、需求、分析与设计、实现、测试、部署）和 **3 个核心支持工作流**（配置与变更管理、项目管理、环境）。

## 六、考点 5：敏捷开发（领会）

### 1. 敏捷开发的基本思想

- **以人为核心**：人是项目成功的关键，强调**团队自组织、面对面沟通、客户全程参与**；
- **迭代与增量**：把项目拆成**短周期迭代（通常 2–4 周）**，每次迭代都交付**可工作的软件增量**；
- **拥抱变化**：需求变化被视为常态，欢迎变更并快速响应；
- **持续交付与持续反馈**：小步快跑、频繁发布、尽早获得用户反馈；
- **以可运行软件作为进度的主要度量**，而非文档；
- **简洁与可持续**：简化不必要的工作与文档，保持稳定的开发节奏。
- **敏捷宣言 4 条价值观**：个体与交互 > 流程与工具；可运行软件 > 详尽文档；客户合作 > 合同谈判；响应变化 > 遵循计划。
- **12 条原则（记关键词）**：尽早持续交付有价值软件；欢迎需求变化；频繁交付；业务与开发每日协作；信任自组织团队；面对面沟通；可运行软件是主要进度度量；可持续开发节奏；追求技术卓越；简洁；自组织团队；定期反思调整。

### 2. 敏捷开发的过程

需求（用户故事/待办列表）→ **迭代循环〔细化需求 → 简单设计 → 编码 → 测试 → 集成〕→ 交付可运行增量 → 评审与回顾 → 调整计划进入下一迭代**。
- 典型 **Scrum 过程**：产品待办列表 → 冲刺计划会议 → 冲刺待办列表 → 冲刺执行（每日站会）→ 可交付增量 → 冲刺评审 → 冲刺回顾 → 下一冲刺。
- 典型 **XP 过程（6 个阶段）**：探索阶段 → 计划阶段 → 迭代到首次发布 → 产品化 → 维护 → 死亡（终止）。

### 3. 敏捷开发的工具（领会，答"工具/实践"）

用户故事与故事墙、**任务板/看板（Kanban）**、**燃尽图（Burn-down Chart）**、速度（Velocity）图、**持续集成/持续交付（CI/CD）**、自动化测试、版本控制与缺陷跟踪（Git、Jira）、协作与即时沟通工具。

### 4. Scrum 模型

- **团队（3 个角色）**：**产品负责人（PO）**——代表客户、管理产品待办列表与优先级；**Scrum Master**——过程促进者，移除障碍、保障规则执行；**开发团队**——跨职能、自组织，通常 5–9 人。
- **3 个工件**：产品待办列表、冲刺待办列表、产品增量（含"完成的定义 DoD"）。
- **冲刺会议（4 类会议）**：
- **冲刺计划会议**：确定冲刺目标，从产品待办中挑选条目形成冲刺待办列表；
- **每日站会（每日 Scrum 例会）**：15 分钟，答"昨天做了什么/今天做什么/有什么障碍"；
- **冲刺评审会议**：向 PO 与干系人**演示可工作增量**，收集反馈、调整待办；
- **冲刺回顾会议**：回顾**过程与协作**，确定改进措施。
- **冲刺（Sprint）特点**：时间盒固定（2–4 周）、冲刺期间**目标与范围不变**、每日同步、结束必须产出可用增量。

### 5. XP 模型（极限编程）的关键任务/实践

- **用户故事**驱动需求，**计划游戏**（发布计划 + 迭代计划）；
- **小规模（小版本）快速发布**；
- **简单设计**（只为当前需求设计）；
- **测试先行：测试驱动开发（TDD）**，单元测试与验收测试；
- **结对编程**；
- **重构**（持续改善结构而不改变行为）；
- **持续集成**；
- **代码集体所有权**；
- **编码规范/统一标准**；
- **现场客户**（客户全程在团队中）；
- **每周 40 小时工作制**（可持续节奏）；
- **隐喻**（用共同比喻描述系统）。
> XP 强调**技术实践 + 客户参与**，适合**需求模糊、变化快、规模较小**的团队项目。

## 七、五种过程模型对比（易出简答/选择）

- **瀑布**：核心特征：线性顺序、文档驱动、阶段评审；适用场景：需求明确稳定、技术成熟；主要缺点：不适应变化、反馈晚、风险后置
- **原型**：核心特征：快速建原型、反复确认需求；适用场景：需求不明确、用户说不清；主要缺点：易被误当成品、质量差、易失控
- **螺旋**：核心特征：迭代 + **风险分析**、瀑布+原型；适用场景：大型、高风险项目；主要缺点：需风险专家、复杂、小项目不经济
- **RUP**：核心特征：**用例驱动、架构中心、迭代增量**；适用场景：中大型、需要规范化过程；主要缺点：过程重、文档多、成本高
- **敏捷**：核心特征：短迭代、拥抱变化、人本、可运行软件；适用场景：需求变化快、中小团队；主要缺点：依赖团队素质与客户参与，文档少、难管理大项目
